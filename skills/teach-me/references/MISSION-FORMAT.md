# MISSION.md Format

The reason the user is learning this topic. Every teaching decision (what to teach next, which lesson to author, which exercises to design) traces back to this. Keep it short — if it runs past a screen it has stopped being a compass and started being a plan.

````md
# Mission: <Topic>

## Why
<1-3 sentences. The concrete real-world goal. What changes in their life or work when they have this skill?
Avoid abstract framing like "to understand X"; push for the underlying outcome.>

## Success looks like
- <a specific, observable thing the user will be able to do>
- <another>

## Constraints
- <time, budget, prior commitments, learning preferences — anything that bounds the approach>

## Out of scope
- <adjacent topics explicitly not chased right now, protecting the zone of proximal development>
````

Rules:

- **One mission per topic folder.** If the user wants to learn two unrelated things, that is two topic folders.
- **Push back on vagueness.** If the user cannot articulate why, interview them before writing anything. A bad mission is worse than no mission.
- **Revise when reality shifts.** When the goal moves, update MISSION.md and add a learning record capturing the change — confirm with the user before changing it.
